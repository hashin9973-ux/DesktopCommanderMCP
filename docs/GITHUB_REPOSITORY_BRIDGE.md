# Desktop Commander GitHub Repository Bridge

The GitHub Repository Bridge uses a GitHub repository for agent-scoped request/response queues. The bridge runs on your computer; GitHub stores each agent's queue files and artifacts, while local Desktop Commander executes the requested tools.

## Connect an account

The Windows x64 portable build includes the official GitHub CLI as its browser sign-in helper and Cloudflare's cloudflared executable for account-free Quick Tunnels. On the first GitHub connection, if no existing GitHub CLI session or `GITHUB_TOKEN`/`GH_TOKEN` is available, the bridge automatically starts:

```powershell
gh auth login --web --hostname github.com --git-protocol https --scopes admin:repo_hook
```

GitHub CLI opens the browser-based device sign-in flow and shows any required one-time verification steps in the bridge window. Complete that approval in the browser; after sign-in, the bridge continues to repository selection without requiring a restart. The GitHub CLI manages the saved credential using the credential store available on the computer. The bridge does not write the token into the repository or Desktop Commander settings.

When running from source or an npm installation rather than the Windows portable build, install GitHub CLI from https://cli.github.com/. If the browser cannot open automatically, run `gh auth login --web --hostname github.com --scopes admin:repo_hook` in a terminal and then restart the bridge.

For headless deployments, set `GITHUB_TOKEN` or `GH_TOKEN` in the process environment instead. Never put a token in a request file or commit it to the repository. The first connection still requires interactive local security consent (type `YES`; and, for a public repository, separately type `PUBLIC`). After the repository-specific consent is saved locally, later starts can run non-interactively.

## Select or create the repository

Start the portable executable and choose **GitHub repository bridge**. The first connection offers two choices:

1. Select an existing, non-archived repository where the authenticated account has write permission. Private repositories are strongly recommended.
2. Create a new repository under the authenticated personal account. The bridge requests that GitHub create it as **private**, initializes it, and prepares the `agents/` namespace.

The created repository is a dedicated queue repository; it is not a clone of your application source repository. To create a private repository through the GitHub API, the credential must have repository-creation permissions. For a fine-grained personal access token, GitHub documents either the Administration or Repository creation repository permission with write access as required for this endpoint; classic tokens need the `repo` scope. See [GitHub's create-a-repository endpoint](https://docs.github.com/en/rest/repos/repos#create-a-repository-for-the-authenticated-user).

You can also configure the selection non-interactively:

```powershell
DesktopCommanderBridge.exe bridge --provider github --github-repository owner/name
DesktopCommanderBridge.exe bridge --provider github --create-github-repository desktop-commander-agents
```

## Queue protocol

The bridge initializes this repository namespace on the existing default branch:

- `agents/<agent-instance-id>/requests/` — submit `<id>.json` or `<id>.md` requests.
- `agents/<agent-instance-id>/responses/` — completed `<id>.json` results for that agent.
- `agents/<agent-instance-id>/artifacts/` — binary outputs and JSON files containing large tool results referenced by a response.
- `agents/.gitkeep` — keeps the agent namespace in Git before the first agent submits work.
- `README.md` — the only agent-facing guide, with quick-start steps, protocol instructions, and every tool's argument schema.

Create one unique folder per conversation or agent instance, not one folder per platform. For example, a ChatGPT conversation can use `chatgpt-7f3a91c2d4e6`; a second simultaneous ChatGPT conversation must use a different suffix such as `chatgpt-2b8e4d6a1c9f`. Never use a shared platform-only folder such as `chatgpt`. Reuse the folder only when continuing that same conversation; every subagent also gets its own unique folder. The folder identifies the individual agent instance, so no bridge registration or shared mailbox ID is needed. Request IDs are unique only inside that folder, which means different conversations may both submit `task-a1` without colliding. The legacy `agents/default/` folder is reserved for migrated root-level data; do not use it for new conversations.

`README.md` is generated by the same guide generator used by Cloud-folder Bridge. It contains the agent-folder layout, AI Quick Start, asynchronous request workflow, response/artifact handling, security guidance, and the complete tool catalog with JSON argument schemas. GitHub mode replaces the selected repository's root `README.md` with this AI guide and removes the legacy `DESKTOP_COMMANDER_BRIDGE.md`; preserve any custom README content elsewhere before connecting.

Requests use protocol version 1 and the same command/tool schemas as Cloud-folder Bridge. A local worker uses the existing Desktop Commander execution engine. By default, GitHub mode starts a loopback-only webhook receiver and Cloudflare Quick Tunnel, then registers a GitHub push webhook for the selected repository's default branch. Push notifications trigger synchronization immediately. A local filesystem watcher also publishes completed responses and their artifacts as soon as the worker writes them; a 60-second reconciliation poll remains active to recover from missed notifications. Use --poll-interval-ms to change the reconciliation interval (1,000–60,000 ms), or --no-github-webhook to use polling only. If the tunnel or webhook cannot be enabled, the bridge falls back to the previous polling interval (5 seconds by default).

Artifacts are uploaded before the response file. The response file is the durable completion marker. Files are committed directly to the repository's existing default branch. The bridge does not create branches, pull requests, or edit application source files.

When a tool result would make the response exceed 1 MB, the bridge automatically moves the largest result fields into `application/json` artifacts and keeps the response marker at or below 1 MB. Large artifact data is split into ordered chunks no larger than 32 MiB each. The artifact reference appears in the command result and at the response level. To reconstruct a chunked artifact, retrieve every file in `parts` order, concatenate the exact bytes, and validate the combined `bytes` and `sha256` before parsing the JSON. The generated AI-facing `README.md` is not modified to handle this case; the retrieval notice is part of the response itself.


## Requirements and limitations

- The selected repository must allow direct writes to its default branch. A public repository requires an additional interactive confirmation because anyone can read its queue contents; the automatically-created option is always private. A branch rule that requires pull requests is incompatible with this no-branches design.
- Use one running bridge worker per repository. GitHub commits are not a distributed worker lock.
- Anyone with write access to the repository can submit commands for local execution on the bridge computer. Use a private repository and share write access only with trusted collaborators. The local tool restrictions are guardrails, not an operating-system sandbox.
- GitHub queue files are limited to 50 MiB each. Response JSON is automatically externalized once the serialized response exceeds 1 MB; artifact uploads are split into verified chunks no larger than 32 MiB to leave room for base64 encoding in Contents API requests without creating a branch commit for every 1 MB slice. GitHub recommends a maximum 1 MB Git object size and a maximum of six pushes per minute per repository; this transport chooses fewer commits per large artifact at the cost of larger-than-recommended artifact objects. This is a repository-health choice, not a GitHub Free-plan 500 MB repository quota: that 500 MB allowance is shared by GitHub Actions artifact storage and GitHub Packages. GitHub recommends keeping repositories under 1 GB. GitHub Repository Bridge retains commit history, so deleting old queue files from the latest tree does not reclaim the historical objects; long-running mailboxes can still grow and must be monitored or periodically migrated/compacted. For a chunked artifact, its `parts` array lists the remote files in reconstruction order; download and concatenate those exact bytes, then verify the artifact's total `bytes` and `sha256`. Its `path` is a logical artifact name when `parts` is present. Requests larger than the 50 MiB queue-file limit are rejected.
- Remote queue history is retained in GitHub; the bridge does not automatically delete remote requests, responses, or artifacts. Repository maintainers can archive or remove old queue entries manually.
- GitHub's Contents API is used for file-level reads and commits. The bridge does not check out the repository or synchronize unrelated source files to the local worker.

## Startup modes

When launched directly in an interactive terminal with no arguments, the portable executable offers **MCP**, **Cloud-folder bridge**, **GitHub repository bridge**, and **Local OpenAI-compatible API (KoboldCpp)**. MCP is the default selection. The Local API mode connects to a local model endpoint and executes Desktop Commander tools directly; it does not use this GitHub queue. See [Local OpenAI-compatible API mode](LOCAL_OPENAI_COMPATIBLE_API.md). When launched by an MCP host without an interactive terminal, the launcher starts standard MCP stdio mode without displaying a menu. Existing explicit `bridge --directory ...` invocations continue to use Cloud-folder Bridge.


## Startup behavior

After the saved GitHub session and repository have been validated, the local worker and five-second polling fallback start without waiting for the full queue scan or Cloudflare tunnel. Queue directory initialization, initial synchronization, and push-webhook setup continue in the background. When the tunnel and webhook are ready, the bridge switches to the configured reconciliation interval; if setup fails, it keeps polling. First-time browser sign-in and the required local security-consent prompts still need user interaction.

## Diagnosing a request that appears stuck

The worker's `Agent <agent-instance-id> request <id>: completed` log means the tool commands finished and a response was written to that agent's local cache. It does not, by itself, prove that GitHub received the response or that the agent retrieved it. The GitHub bridge logs each staged `agents/<agent-instance-id>/requests/<id>.*` item and each published `agents/<agent-instance-id>/responses/<id>.json`. Compare both the agent folder and request ID across those messages:

- No request file under `agents/<agent-instance-id>/requests/`: that agent or its storage connector did not submit the request.
- Request in GitHub, but no staged log: the bridge has not downloaded it; inspect synchronization errors and API rate-limit pauses.
- Staged log, but no `Agent <agent-instance-id> request <id>:` completion: the local worker or an executing tool is still processing it, or the worker stopped.
- Worker completion, but no published log: the local response exists but GitHub synchronization has not published it; inspect the queue synchronization error.
- Published log and matching `agents/<agent-instance-id>/responses/<id>.json` on GitHub: the bridge completed that agent's round trip. Failure to retrieve or continue from that response is on the agent/storage-connector side.

On Windows, a new local GitHub cache is under `%LOCALAPPDATA%\DesktopCommanderBridge\github-cache\<repository-id>\`. The worker's durable ledger is under `%LOCALAPPDATA%\DesktopCommanderBridge\github-worker-state\<repository-id>\localappdata\DesktopCommanderBridge\requests\<agent-instance-id>\<id>.json`; its `updated_at` and command states show the last recorded execution step. Legacy caches may retain their previous owner/name path after same-repository migration.

GitHub rate-limit responses are no longer retried on every poll. The bridge honors Retry-After and primary-limit reset headers, and uses increasing pauses when GitHub reports a secondary limit without a retry hint. The console error includes the next retry time.

Request IDs are one-use idempotency keys within one agent folder. If `agents/<agent-instance-id>/responses/<id>.json` already exists, a later request from that same agent with the ID is skipped to prevent duplicate side effects. Different agents may reuse the same ID because their request, response, artifact, and ledger paths are separate. Do not overwrite an existing request file to retry different work; submit it under a new ID for that agent. While the bridge is running, it warns if it sees a changed request blob under an already-completed ID.

## Push notifications and Quick Tunnel

GitHub mode uses a Cloudflare Quick Tunnel to receive signed GitHub push webhook deliveries without opening an inbound router port or requiring a Cloudflare account or custom domain. The local webhook server binds only to 127.0.0.1; the public tunnel exposes only a dedicated webhook route, not the Desktop Commander worker or tool interface.

The portable Windows build includes the official cloudflared executable. Other installations need cloudflared available on PATH. Quick Tunnels are temporary development tunnels: their hostname changes on each start and they have no uptime guarantee. The bridge stores a random webhook secret locally, validates GitHub's X-Hub-Signature-256 HMAC before accepting an event, and subscribes only to push events on the selected repository's default branch. The webhook secret is not written to the repository.

Creating or updating a repository webhook requires repository owner/admin access and webhook-write permission. GitHub CLI browser sign-in requests the OAuth admin:repo_hook scope; an existing CLI session may prompt once to refresh that scope. A fine-grained personal access token supplied through GITHUB_TOKEN or GH_TOKEN needs the repository Webhooks: write permission. If the credential does not have the required permission, or the Quick Tunnel cannot start, the bridge continues with polling instead.

Cloudflare Quick Tunnels are intended for development and testing and do not provide an uptime guarantee. The slower reconciliation poll recovers from missed webhook notifications while the bridge is running. When the bridge is stopped, its ephemeral tunnel is closed; the next startup updates the saved repository webhook to the new URL.
