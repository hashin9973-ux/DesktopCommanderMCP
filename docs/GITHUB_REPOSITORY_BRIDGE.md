# Desktop Commander GitHub Repository Bridge

The GitHub Repository Bridge uses a GitHub repository as a request/response mailbox. The bridge runs on your computer; GitHub stores queue files and artifacts, while local Desktop Commander executes the requested tools.

## Connect an account

The Windows x64 portable build includes the official GitHub CLI as its browser sign-in helper and Cloudflare's cloudflared executable for account-free Quick Tunnels. On the first GitHub connection, if no existing GitHub CLI session or `GITHUB_TOKEN`/`GH_TOKEN` is available, the bridge automatically starts:

```powershell
gh auth login --web --hostname github.com --git-protocol https --scopes admin:repo_hook
```

GitHub CLI opens the browser-based device sign-in flow and shows any required one-time verification steps in the bridge window. Complete that approval in the browser; after sign-in, the bridge continues to repository selection without requiring a restart. The GitHub CLI manages the saved credential using the credential store available on the computer. The bridge does not write the token into the repository or Desktop Commander settings.

When running from source or an npm installation rather than the Windows portable build, install GitHub CLI from https://cli.github.com/. If the browser cannot open automatically, run `gh auth login --web --hostname github.com --scopes admin:repo_hook` in a terminal and then restart the bridge.

For headless deployments, set `GITHUB_TOKEN` or `GH_TOKEN` in the process environment instead. Never put a token in a request file or commit it to the repository. The first connection still requires interactive local security consent (type `YES`; and, for a public repository, separately type `PUBLIC`). After the repository-specific consent is saved locally, later starts can run non-interactively.

## Select or create the repository

Start the portable executable and choose **GitHub repository bridge**. The first connection offers two choices:

1. Select an existing, non-archived repository where the authenticated account has write permission. Private repositories are strongly recommended.
2. Create a new repository under the authenticated personal account. The bridge requests that GitHub create it as **private**, initializes it, and then creates the queue folders.

The created repository is a dedicated mailbox; it is not a clone of your application source repository. To create a private repository through the GitHub API, the credential must have repository-creation permissions. For a fine-grained personal access token, GitHub documents either the Administration or Repository creation repository permission with write access as required for this endpoint; classic tokens need the `repo` scope. See [GitHub's create-a-repository endpoint](https://docs.github.com/en/rest/repos/repos#create-a-repository-for-the-authenticated-user).

You can also configure the selection non-interactively:

```powershell
DesktopCommanderBridge.exe bridge --provider github --github-repository owner/name
DesktopCommanderBridge.exe bridge --provider github --create-github-repository my-private-mailbox
```

## Queue protocol

The bridge initializes these repository paths on the existing default branch:

- `requests/` — submit `request-<id>.json` or `request-<id>.md`.
- `responses/` — completed `response-<id>.json` files.
- `artifacts/` — binary outputs and JSON files containing large tool results referenced by a response.
- `README.md` — the shared AI-facing guide with quick-start steps, protocol instructions, and every tool's argument schema.

`README.md` is generated by the same guide generator used by Cloud-folder Bridge. It contains the AI Quick Start, asynchronous request workflow, response/artifact handling, security guidance, and the complete tool catalog with JSON argument schemas. GitHub mode replaces the selected repository's root `README.md` with this AI guide and removes the legacy `DESKTOP_COMMANDER_BRIDGE.md`; preserve any custom README content elsewhere before connecting.

Requests use protocol version 1 and the same command/tool schemas as Cloud-folder Bridge. A local worker uses the existing Desktop Commander execution engine. By default, GitHub mode starts a loopback-only webhook receiver and Cloudflare Quick Tunnel, then registers a GitHub push webhook for the selected repository's default branch. Push notifications trigger synchronization immediately. A local filesystem watcher also publishes completed responses and their artifacts as soon as the worker writes them; a 60-second reconciliation poll remains active to recover from missed notifications. Use --poll-interval-ms to change the reconciliation interval (1,000–60,000 ms), or --no-github-webhook to use polling only. If the tunnel or webhook cannot be enabled, the bridge falls back to the previous polling interval (5 seconds by default).

Artifacts are uploaded before the response file. The response file is the durable completion marker. Files are committed directly to the repository's existing default branch. The bridge does not create branches, pull requests, or edit application source files.

When a tool result is too large to embed in the response, the bridge writes the complete original result content to an `application/json` artifact and replaces the inline content with a notice that the output was too large and moved to the referenced artifact. The artifact reference appears in the command result and at the response level. For chunked artifacts, retrieve every file in `parts` order, concatenate the exact bytes, and validate the combined `bytes` and `sha256` before parsing the JSON. The generated AI-facing `README.md` is not modified to handle this case; the retrieval notice is part of the response itself.


## Requirements and limitations

- The selected repository must allow direct writes to its default branch. A public repository requires an additional interactive confirmation because anyone can read its queue contents; the automatically-created option is always private. A branch rule that requires pull requests is incompatible with this no-branches design.
- Use one running bridge worker per repository. GitHub commits are not a distributed worker lock.
- Anyone with write access to the repository can submit commands for local execution on the bridge computer. Use a private repository and share write access only with trusted collaborators. The local tool restrictions are guardrails, not an operating-system sandbox.
- GitHub queue files are limited to 50 MiB each. The transport uploads artifact files in verified chunks no larger than 32 MiB, leaving headroom for base64 encoding in the Contents API request. Large text or structured tool results are moved into JSON artifacts so the response completion marker remains small. For a chunked artifact, its `parts` array lists the remote files in reconstruction order; download and concatenate those exact bytes, then verify the artifact's total `bytes` and `sha256`. Its `path` is a logical artifact name when `parts` is present. Requests larger than the 50 MiB queue-file limit are rejected.
- Remote queue history is retained in GitHub; the bridge does not automatically delete remote requests, responses, or artifacts. Repository maintainers can archive or remove old queue entries manually.
- GitHub's Contents API is used for file-level reads and commits. The bridge does not check out the repository or synchronize unrelated source files to the local worker.

## Startup modes

When launched directly in an interactive terminal with no arguments, the portable executable offers **MCP**, **Cloud-folder bridge**, **GitHub repository bridge**, and **Local OpenAI-compatible API (KoboldCpp)**. MCP is the default selection. The portable folder also includes **Choose Desktop Commander Mode.cmd**, which explicitly opens this menu, and **Start Local OpenAI API (KoboldCpp).cmd**, which starts Local API mode directly. Use these launchers when starting from File Explorer or a shell that does not expose interactive TTY streams. The Local API mode connects to a local model endpoint and executes Desktop Commander tools directly; it does not use this GitHub queue. See [Local OpenAI-compatible API mode](LOCAL_OPENAI_COMPATIBLE_API.md). When launched by an MCP host without an interactive terminal, the executable starts standard MCP stdio mode without displaying a menu so the MCP protocol stream remains clean. Existing explicit `bridge --directory ...` invocations continue to use Cloud-folder Bridge.


## Push notifications and Quick Tunnel

GitHub mode uses a Cloudflare Quick Tunnel to receive signed GitHub push webhook deliveries without opening an inbound router port or requiring a Cloudflare account or custom domain. The local webhook server binds only to 127.0.0.1; the public tunnel exposes only a dedicated webhook route, not the Desktop Commander worker or tool interface.

The portable Windows build includes the official cloudflared executable. Other installations need cloudflared available on PATH. Quick Tunnels are temporary development tunnels: their hostname changes on each start and they have no uptime guarantee. The bridge stores a random webhook secret locally, validates GitHub's X-Hub-Signature-256 HMAC before accepting an event, and subscribes only to push events on the selected repository's default branch. The webhook secret is not written to the repository.

Creating or updating a repository webhook requires repository owner/admin access and webhook-write permission. GitHub CLI browser sign-in requests the OAuth admin:repo_hook scope; an existing CLI session may prompt once to refresh that scope. A fine-grained personal access token supplied through GITHUB_TOKEN or GH_TOKEN needs the repository Webhooks: write permission. If the credential does not have the required permission, or the Quick Tunnel cannot start, the bridge continues with polling instead.

Cloudflare Quick Tunnels are intended for development and testing and do not provide an uptime guarantee. The slower reconciliation poll recovers from missed webhook notifications while the bridge is running. When the bridge is stopped, its ephemeral tunnel is closed; the next startup updates the saved repository webhook to the new URL.
